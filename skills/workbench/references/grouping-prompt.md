# 差分レビュー — グルーピングと理由文の生成規則

抽出済みの差分要素を受け取り、レビュー画面に出す JSON を返す。

## 入力

- **決定要素（ファイル操作）** — ファイルの移動・追加・削除をまとめたもの。中身の変更を伴わない移動も含む
- **核候補 hunk** — 機械判定で「機械的な置換ではない」と判定された hunk
- **波及 hunk の集計** — 機械的な置換として畳まれた hunk の件数

## グルーピングの規則

グループとは **1つの決定と、それが引き起こした変更のまとまり** である。

- 意図を1文で言えないなら、そのグループは大きすぎる。分割する
- ファイル操作も hunk と同格の要素として扱う。配置を変えることは決定である
- 核が複数あるグループは分割する。ただし同じ波及を共有している場合は親グループに残してよい
- 種別（feat / refactor / test）やディレクトリでまとめない。決定でまとめる

各グループについて、要素を **核** と **波及** に分ける。

- 核 = その決定そのものを表す要素。人間が判断すべきもの
- 波及 = 核を承認すれば自動的に承認されるもの
- グループ内で相対的に決める。グループに既に決定があるなら、残りは波及に落とす

## 理由文の規則

各グループに、**なぜ人間がこれを読む必要があるか**を1文で書く。

差分を読めば分かることは書かない。書くのは **その方法を選んだ理由と、その選択が外れたときに何が起きるか** だけである。

1. **決定の動詞で書く。** 「〜にした」「〜を選んだ」。受動態（「〜されています」「〜が変更されました」）を使わない
2. **代替案か破綻条件を必ず1つ含める。** 「他に〜もありえた」または「〜のとき壊れる」
3. **120字以内。** 下限はない。短くて済むなら短くする
4. **書けないときは書かない。**

### 4 の判定手順（必ず実行する）

理由文の草稿から、**「何をしたか」を述べている部分を全て消す。** 残ったものを見る。

- 何も残らない → その理由文は差分の言い換えである。**理由文を空にし `意図不明` を立てる**
- 「なぜその方法か」または「何が壊れるか」が残る → その理由文を採用する

「〜を削除した」「〜を追加した」「〜に変更した」は常に1文で書けてしまう。**書けたことは、書く価値があったことを意味しない。** 与えられた情報からその選択の理由が読み取れないなら、`意図不明` を立てるのが正しい出力である。埋めた方が親切に見えるが、判断材料にならない1文は人間の時間を奪うだけになる。

### 差分の外にある事実

差分に写っていないが判断に必要な事実は、理由文に持ち込む。
呼び出し先のシグネチャ、返り値の型、呼び出し元の件数など。

持ち込むときは必ず `file:line` を添える。
人間が裏を取れない主張を書かせないため。

評価を書かない。「良い設計です」「適切です」「問題ないと思われます」は禁止。事実と分岐点だけを書き、判断は人間に残す。

位置は必ず要素の ID で指す。「この関数」「上記の処理」のような指示語で済ませない。

## タグ

グループに立てる。複数可。

- `設計判断` — 代替案がありえた箇所
- `plan外` — plan に対応する項目がない（plan が与えられていない場合は立てない）
- `破壊的` — 削除、公開シンボルの変更、テストの削除
- `意図不明` — 理由文が書けなかった
- `機械的` — 読まなくてよい

## 出力

```json
{
  "groups": [{
    "id": "g1",
    "title": "<名詞句>",
    "tags": ["設計判断"],
    "reason": "<理由文、書けなければ空文字>",
    "core": ["h029", "f003"],
    "ripple": ["h030"],
    "rippleCount": 12
  }]
}
```
