# skill-audit

行数・symlink・frontmatter・リンク切れは `~/.claude/hooks/skill-lint.py` が決定的に見る。
ここで扱うのは**複数の skill を並べないと分からないこと**だけである。

定期実行しない。**工程が動いたときに走らせる。**

## 1. lint を先に通す

    python3 ~/.claude/hooks/skill-lint.py <対象>

構造の問題が残っていると、読み手がそれを報告して指摘が埋もれる。0 件にしてから始める。

## 2. 対象と fork 元を並べる

対象は `<対象>/.agents/skills/`（無ければ `.claude/skills/`）の各 skill。

**fork 元は推測しない。** skill 直下の `AUDIT.md` の `fork 元:` から引く。
`AUDIT.md` が無い skill は `fork-drift` の対象外とする。

以前は「共通 skill を名指ししているか」で判定していたが、`land-worktree` も `open-worktree` も
「呼ぶな」「案内せよ」の文脈で `start-implementation` を名指しており、無関係な組ができた。
名指しの向きは本文からは決まらない。

**`implement-approved-plan` の「`/start-implementation` を読むな」はここに適用されない。**
あれは実装中のエージェントが再計画を始めるのを防ぐ規約であって、着地後に main で走る監査は対象外である。

## 3. 読み手を起動する

**1 skill 1 体、`haiku`、読み取り専用 (`Explore`)。** 独立なので同じメッセージでまとめて起動する。

読み手には [references/rubric.md](references/rubric.md) の中身と、対象 skill のパスだけを渡す。
**他の skill も、それがどう使われているかも渡さない。** 文脈を持つと深刻度を判定し始め、
突き合わせという主エージェントの仕事を奪う。

読み手の仕事は 2 つで、どちらも**判定ではない**。

- **抽出** — 手順・生む成果物・参照する成果物・述べている規律を、逐語で 1 行 1 件
- **観測** — `stale-reference` のみ。1 文書で閉じるのでこれだけは読み手が見つけられる

`fork-drift` `artifact-name-drift` `duplicate-source` を読み手に探させない。
**不在と文書間の不一致は、モデルではなく差集合で出す。**

## 4. 突き合わせる

`artifact-name-drift` と `duplicate-source` は、抽出された行を集合として主エージェントが判定する。

| 観点 | 判定 |
|---|---|
| `artifact-name-drift` | どの `produces` にも無い `references` の名前。**`tmp/` 配下の成果物だけを比べる** |
| `duplicate-source` | 同じ `rule` が 2 つ以上の skill に現れる。表記の揺れがあるので近似一致で見る |

**fork 元を `duplicate-source` の対象にしない。** fork 先が fork 元の規律を写すのは fork そのもので、
`AUDIT.md` が「落とした」「形を変えた」を持っている以上、**残りは写したものだと既に表現されている**。
対象に入れると意図的な重複が毎回出て、直す気のないものを読まされる。写した規律の一覧も作らない。
fork 元から差分を引けば求まるものを手で並べると、三重目の写しになって腐る。

**自己完結のための最小限の再掲は重複ではない。** skill は 1 本ずつ読まれるので、
`land-worktree` と `open-worktree` がどちらも「追跡外の `tmp/` は汚れに数えない」を持つのは正しい。
報告するのは、再掲では説明できない量の重複と、同じ手順が 2 本にあって片方だけ直されている場合である。

`artifact-name-drift` を全ファイル名で比べない。skill 群の外で作られるもの
(`.claude/impl-workflow.md`、別リポジトリの文書、skill 自身の `references/`) が全部引っかかり、
実際に 15 件出て全部が正しい参照だった。名前がずれるのは skill 間で受け渡す成果物だけで、
それは `tmp/<NNNN_name>/` にしかない。外部ファイルの実在は `skill-lint` が見る。

### fork-drift だけは読み手に判定させる

**この 1 観点だけ、読み手に 2 文書を渡す。rubric の「1 文書だけ」の例外である。**

手順名の集合差では判定できない。fork 先は工程を全面的に改名するので、
同じ工程でも文字列が重ならない (`7. 承認後に実装する` と `## 3. codex を起動する`)。

読み手に渡すのは、fork 元の `SKILL.md`、fork 先の `SKILL.md`、
そして fork 先の `AUDIT.md` の「落とした工程」の一覧である。訊くのは 1 つだけにする。

> **一覧に挙がっていない欠落があるか。** 挙がっているものは意図して落としたので報告しない。

一覧の各引用が fork 元に実在するかは `skill-lint` が既に照合しているので、ここでは見ない。

## 5. 照合する

すべての行の `quote` を、実ファイルの該当行と突き合わせる。**一致しないものは捨てる。**
安いモデルの誤検出をそのまま人へ出さない。同じ箇所への重複は 1 件にまとめる。

**バッククォート・太字・空白を無視して比べる。** 読み手はこれらを落として引用するので、
そのまま比べると正確な観測が 1 割ほど落ちる。行番号も前後 2 行までずれを許す。
記号を無視しても一致しないものが、本当に本文に無い引用である。

## 6. 仕分ける

生き残ったものを、自分で読んで確かめたうえで 3 つに分ける。

| 区分 | 条件 | 扱い |
|---|---|---|
| **直す** | 正しい姿が一意に決まる。成果物名の統一、参照先の付け替えなど | 直してから報告する |
| **出す** | 工程を足す・移す・消す判断を伴う。どちらが正本か一意に決まらない | 直さずに提示する |
| **捨てる** | 読んで確かめたら問題なかった | 報告しない。理由も書かない |

**`fork-drift` は必ず出す。** 工程を戻すかどうかは fork した理由に依るので、一意に決まらない。

## 7. 提示する

```text
直した: <file>:<line> — <何がどう食い違っていたか> → <どう直したか>

要判断: <何が起きているか、skill 名を知らなくても分かる 1 文>
  該当箇所: 「<本文からの引用>」
  選択肢: <A> | <B>
```

要判断が 1 件も無ければ「要判断なし」と言い切る。無理に残さない。

## やらないこと

- 構造の指摘を重ねて報告しない (`skill-lint` の仕事)
- 読み手の観測をそのまま人へ流さない (照合を挟む)
- 指摘を埋めるために無理に問題を作らない
