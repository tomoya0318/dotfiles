# ADR を扱う

## 作業を分類する

依頼を次のいずれかに分類してから作業する。

- **新規作成**：決定課題と、一つ以上の現実的な案または避けられない制約が存在する。
- **提案中 ADR の改訂**：状態が「提案」の既存 ADR を更新する。
- **レビュー**：内容を評価し、明示的に編集を求められていなければ指摘だけを返す。
- **確定済み ADR の変更**：状態が「採用」「却下」「非推奨」「置換済み」の ADR は、必要に応じて後継 ADR を作る。

決定課題も検討案も定まっていない調査段階では ADR を作らない。
合意前でも、具体的な決定課題と検討案があれば「提案」の ADR を作ってよい。

## ADR にする判断を見極める

構造、主要な依存関係、公開インターフェース、品質要件、採用技術、開発方式など、後から変更しにくく長期的な影響を持つ判断を記録する。

一つの ADR には、独立して変更または撤回できる一つの判断だけを記録する。
調査メモ、実装手順、定例作業の記録、決定理由を伴わない要約には使わない。

作業前に、関連するコード、設定、設計資料、issue、既存 ADR を確認する。
確認できない事実や、実際には検討していない選択肢を補わない。

## プロジェクトルートを確定する

次の順で保存対象のプロジェクトルートを決める。

1. ユーザーが明示したルートを使う。
2. 対象ファイルから祖先をたどり、既存の `ai-guide/adr` を持つ最も近いディレクトリを使う。
3. 単一プロジェクトのリポジトリなら、対象ファイルを含む Git ルートを使う。
4. モノレポでリポジトリ全体と個別プロジェクトのどちらが判断を所有するか不明なら、作成前に確認する。

ルートが確定するまで `ai-guide/adr` を新設しない。
保存先は `<project-root>/ai-guide/adr` とする。

## 新しい ADR を作成する

既存 ADR を検索し、同じ判断の重複や置換対象がないか確認する。

この `SKILL.md` があるディレクトリと確定したプロジェクトルートを、それぞれ絶対パスとして設定する。
次のスクリプトで、既存の最大番号に続く ADR を作成する。

```sh
SKILL_DIR="/absolute/path/to/adr-writing"
PROJECT_ROOT="/absolute/path/to/project"

sh "$SKILL_DIR/scripts/new_adr.sh" \
  --project-root "$PROJECT_ROOT" \
  --title "決定を表す日本語の題名" \
  --slug "short-english-slug"
```

合意前は既定の「提案」を使う。
すでに採用済みの判断を初めて記録する場合だけ `--status 採用` を付ける。
後継 ADR を作る場合は `--related-adr` に旧 ADR への Markdown リンクを渡す。

連番を手で決めたり、既存ファイルを上書きしたりしない。
作成先は `<project-root>/ai-guide/adr/NNNN-short-english-slug.md` とする。
slug は小文字英数字と単一ハイフンだけを使い、判断を区別できる短い英語名にする。

## 内容を書く

[assets/adr-template.md](assets/adr-template.md) の各 HTML コメントに答える。
コメントは執筆用の問いであり、完成した ADR からすべて削除する。

二つ以上の実質的な選択肢がある場合は、同じ判断基準で比較する。
選択の余地がない場合は、選択を制約した事実を背景と判断基準に書く。

決定と実装計画を混同しない。
ADR には何を選び、なぜ選び、何を引き受けるかを書く。
作業順序や詳細なタスクは必要最小限にとどめ、issue や計画書へリンクする。

個人開発を前提とし、決定者、承認者、所有者のフィールドは設けない。
メタデータの「関連 ADR」には置換元、置換先、直接依存する ADR だけを書く。
issue、設計資料、ベンチマーク、計測結果は本文の「参考資料」に書く。

## 日本語を整える

一文ごとに改行し、一つの段落には一つの論点だけを置く。
題名は「何を採用、統一、禁止、維持するか」が分かる形にする。
決定節の最初の一文で、選んだものを明示する。

背景は時系列の記録ではなく、判断を必要にした事実と制約から書く。
根拠が確認できる事実は具体的に書き、仮定や将来予測には不確実性を残す。
専門用語は必要な範囲だけ定義し、以後は同じ語を使う。

情報を増やさない定型句、進行実況、読者への問いかけ、劇的な転回、未解決の問いを残す演出は使わない。
将来の読者が判断を再現できる簡潔な記録にする。

## 状態と履歴を扱う

状態は次の五つだけを使う。

- **提案**：合意前。レビューに合わせて本文を更新してよい。
- **採用**：現在採用している判断。
- **却下**：採用しないと決めた提案。
- **非推奨**：判断は履歴として残るが、今後の利用を推奨しない。
- **置換済み**：後継 ADR によって置き換えられた判断。

「却下」へ変更する前に `## 却下理由` を追加し、再検討に必要な理由を書く。
「非推奨」には、その理由または現在の方針を示す関連 ADR を設定する。
「置換済み」には、後継 ADR を関連 ADR として設定する。

採用後の事情変更では新しい ADR を作る。
新しい ADR から旧 ADR へリンクし、新しい ADR が採用された時点で旧 ADR を「置換済み」にして相互にリンクする。
このとき旧 ADR で変更してよいのは「状態」と「関連 ADR」だけとし、説明注記や新しい節を追加しない。

確定済み ADR の判断、根拠、影響を後から書き換えない。
判断の解釈を変えない明白な誤字、壊れたリンク、Markdown の書式だけは修正してよい。
意味が変わる可能性がある修正は後継 ADR で扱う。

## 完成前に点検する

- 題名、ファイル名、文書内の番号が一致している。
- 状態と日付が有効で、関連 ADR の役割が明確である。
- 空の節、HTML コメント、プレースホルダーが残っていない。
- 判断が必要な背景、比較軸、選択肢、決定理由、影響、検証方法を追跡できる。
- 選択肢の比較と最終判断が同じ判断基準を使っている。
- 既存 ADR と矛盾する場合は、後継関係を相互に記録している。
- 確定済み ADR の意味を直接書き換えていない。
